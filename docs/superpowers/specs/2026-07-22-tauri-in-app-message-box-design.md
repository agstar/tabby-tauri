# Tauri 应用内消息框设计

日期：2026-07-22

## 背景

Tauri 版本当前通过 Rust 命令调用 Windows `MessageBoxW` 显示确认框。该消息框没有绑定 Tabby 主窗口句柄，因此可能出现在应用窗口之后，只在任务栏留下提示。同时，前端会等待原生消息框返回；用户看不到消息框时，终端表现为无法操作，容易被误认为程序卡死。

多行粘贴确认是该问题最明显的入口，但 `PlatformService.showMessageBox` 是通用能力，因此修复应覆盖 Tauri 中所有消息框，而不是只为多行粘贴增加特例。

## 目标

- Tauri 中所有 `showMessageBox` 都显示在 Tabby 应用窗口内部。
- 弹窗打开时有清晰的模态遮罩，不再产生隐藏在后台的独立系统窗口。
- 保持现有调用接口和返回值约定，调用方无需感知平台实现变化。
- 多行粘贴弹窗按 Enter 时默认继续粘贴；按 Esc 或关闭时取消。
- 长文本和多行文本保持原始换行，并在受限区域内滚动。
- 弹窗关闭后恢复原先的终端输入焦点。
- 移除 Tauri 中不再使用的 Windows 原生消息框实现，防止后续重新走到有缺陷的路径。

## 非目标

- 不改变 Electron 平台现有的原生消息框实现。
- 不改变多行粘贴检测规则、预览长度或配置项。
- 不重新设计所有 Tabby 模态框的视觉系统。
- 不改变现有按钮顺序、`defaultId` 和 `cancelId` 的调用语义。

## 方案比较

### 方案 A：在 `tabby-core` 中提供共享消息框组件（采用）

将现有 Web 消息框组件迁移为 Core 共享组件，由 Web 和 Tauri 的平台服务分别通过 `NgbModal` 打开。

优点：

- Web 与 Tauri 共用一套交互、模板和键盘行为。
- `MessageBoxOptions` 已定义在 Core，组件归属与数据契约一致。
- 后续修复和样式调整只维护一处。

代价：

- 会同时修改 Core、Web 和 Tauri 三个模块。
- 需要调整模块声明与导出。

### 方案 B：在 `tabby-tauri` 中新增专用组件

只修改 Tauri，在该包内复制一套应用内消息框。

优点是改动面较小；缺点是与 Web 组件重复，键盘、焦点和样式行为容易逐渐分叉。因此不采用。

### 方案 C：修复 Windows 原生消息框的父窗口与线程模型

向 `MessageBoxW` 传入主窗口句柄，并调整同步调用方式。

该方案仍是应用外系统窗口，无法完全消除窗口层级和焦点差异，也不满足“改成应用内弹窗”的目标。因此不采用。

## 架构设计

### 共享组件

在 `tabby-core` 中提供 `MessageBoxModalComponent`，由 Core 模块声明并从公共入口导出。组件接收现有 `MessageBoxOptions`，负责：

- 渲染标题、消息、详细内容和按钮；
- 根据 `defaultId` 标记并聚焦默认按钮；
- Enter 返回 `defaultId`；
- Esc、关闭按钮或取消动作返回 `cancelId`；
- 使用静态遮罩，避免点击终端区域意外关闭弹窗；
- 对详细内容保留空白和换行，并限制最大高度、允许内部滚动。

Web 平台改为引用 Core 中的共享组件，删除原有重复组件。此调整不改变 Web 行为，只统一组件来源。

### Tauri 平台接入

`TauriWindowsPlatformService` 注入 `NgbModal`，其 `showMessageBox`：

1. 记录弹窗打开前的活动元素。
2. 通过 `NgbModal` 打开共享组件，配置静态遮罩。
3. 将调用参数传给组件。
4. 正常选择按钮时返回对应按钮索引。
5. 弹窗被取消或关闭时返回 `cancelId`。
6. 完成后恢复此前元素的焦点；若此前焦点不可用，则让现有终端焦点逻辑接管。

外部调用仍保持 `Promise<{ response: number }>`，因此多行粘贴等调用方无需修改。

### Rust 清理

删除 Tauri Rust 侧的 `show_message_box` 命令、Windows `MessageBoxW` 相关结构、转换逻辑、命令注册和专用测试。Rust 后端不再参与普通确认框展示。

## 交互行为

多行粘贴继续使用两个按钮：继续粘贴和取消。调用方现有的 `defaultId: 0` 保持不变，因此：

- 点击“继续粘贴”或按 Enter：执行粘贴；
- 点击“取消”、按 Esc 或关闭弹窗：不粘贴；
- 弹窗存在期间，遮罩和前景对话框明确说明应用正在等待选择；
- 关闭后焦点回到终端，用户可以继续输入。

其他 Tauri 消息框继续遵循各调用方传入的按钮、默认项和取消项。

## 异常与边界处理

- `defaultId` 缺失或超出按钮范围时不聚焦默认按钮，按 Enter 不触发任何按钮。
- 弹窗 Promise 被 NgbModal 以关闭原因拒绝时，平台层统一映射到 `cancelId ?? 1`，与现有 Web 行为一致，不向调用方泄漏未处理的 rejection。
- 详细内容为空时不渲染空白预览区域。
- 长内容只在弹窗内部滚动，不让弹窗突破可视区域。
- 本次不增加消息框队列；现有调用路径没有并发消息框需求，避免引入未被需求证明的状态管理。

## 测试策略

遵循先写失败测试、再实现的顺序：

1. 更新 Tauri 渲染器测试，断言 `showMessageBox` 通过 `NgbModal` 和共享组件展示，不再调用 Rust `show_message_box`。
2. 覆盖按钮结果、Enter 默认项、Esc/关闭取消项以及 Promise 取消映射。
3. 覆盖多行详细内容的保留换行与滚动样式契约。
4. 更新 Web 相关测试或静态契约，确保其引用 Core 共享组件。
5. 更新 Rust 测试，确认原生命令及命令注册已移除。
6. 运行变更范围的单元测试、类型检查和 lint。
7. 运行 Tauri 前端构建与 Rust 测试/构建。
8. 对构建产物执行启动冒烟检查，并替换 `bin` 下的软件。

## 验收标准

- 多行粘贴时，确认框始终显示在 Tabby 窗口内部且有遮罩。
- 弹窗打开时不会产生单独的 Windows 任务栏窗口。
- Enter 默认继续粘贴，Esc 和关闭操作取消粘贴。
- 弹窗关闭后终端立即恢复可输入状态。
- Tauri 所有 `showMessageBox` 调用均走共享应用内组件。
- Rust 中不存在可被调用的 `show_message_box` 命令。
- 相关测试、类型检查、前端构建与 Rust 构建通过。
- `bin` 下的软件已替换为验证通过的新构建。
